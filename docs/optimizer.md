# SQLSense AI - Query Optimizer & Candidate Generation

The SQLSense AI optimizer generates multiple candidate queries from different optimization engines and evaluates them through a rigorous validation and cost comparison pipeline.

## Candidate Generation Engines

```
Input SQL
  │
  ├── Candidate A: Relational Algebra (Predicate Pushdown, Constant Folding, Sargability)
  ├── Candidate B: Dynamic Programming Join Optimizer (DP[subset] Join Reordering)
  ├── Candidate C: Index Advisor (Access Path DDL with Query Alignment)
  └── Candidate D: RAG-Augmented Structured Gemini AI Generation
  │
  ▼
Candidate Pool & 7-Stage Validation Pipeline
  │
  ▼
Cost Comparison & Benchmark Verification
  │
  ▼
Evidence-Based Recommendation
```

1. **Relational Algebra Optimizer**: Deterministically applies equivalence-preserving transformations without database round-trips.
2. **DP Join Optimizer**: Computes subset costs ($DP[subset]$) for multi-table queries to identify lowest estimated cardinality access sequences.
3. **Index Advisor**: Identifies missing indexes on filter/join/sort columns with composite ordering (equality $\rightarrow$ range $\rightarrow$ sort).
4. **Structured Gemini Candidate**: Backend-only LLM candidate with strict Zod schema validation and explicit refusal to invent non-existent schema elements.

# SQLSense AI - 7-Stage Candidate Validation Pipeline

Every candidate query (whether generated by rule, relational algebra, DP join optimizer, or Gemini AI) MUST pass the 7-stage validation pipeline:

1. **Syntax Validation**: Ensures candidate is syntactically valid SQL for the target dialect.
2. **Safety Validation**: Blocks unauthorized destructive statements (`DROP`, `TRUNCATE`, `ALTER`, or unconstrained `DELETE`/`UPDATE`).
3. **Semantic Validation**: Verifies referenced tables, projected expressions, and filtering logic preserve original query intent.
4. **Schema Validation**: Validates all referenced columns and tables exist in the target database catalog.
5. **EXPLAIN Validation**: Validates the candidate by running physical `EXPLAIN` against the target database without execution.
6. **Cost Comparison**: Evaluates estimated physical plan cost against original query cost to ensure optimization improvement.
7. **Safe Read-Only Benchmarking**: Runs warm-up and multi-iteration execution timing in a sandboxed read-only transaction to compute measured speedup.
